## M-4: WebSocket Token 不暴露在 URL 中（P1）

### 问题描述

当前设备互联 WebSocket 连接通过 URL 查询参数传递 proxyToken：

```
wss://api.cct.zdzz.top/api/devices/ws?token=<proxyToken>&deviceId=xxx&...
```

URL 查询参数会被以下位置记录，存在 Token 泄露风险：
- Nginx / 反向代理 access log
- 浏览器扩展（可拦截 WebSocket 连接）
- 网络监控工具（Wireshark、企业代理等）

### 需求

后端 WebSocket 端点 `/api/devices/ws` 支持以下任一方式传递 Token（不通过 URL 查询参数）：

#### 方案 A：`Sec-WebSocket-Protocol` 头传递（推荐）

客户端在 WebSocket 握手时通过 `Sec-WebSocket-Protocol` 头传递 Token：

```
GET /api/devices/ws?deviceId=xxx&deviceType=desktop&... HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Protocol: bearer.<proxyToken>
```

后端从 `Sec-WebSocket-Protocol` 头解析 Token，验证后将 `bearer.<proxyToken>` 从响应的 `Sec-WebSocket-Protocol` 中移除（返回空或标准协议名）。

**优点**：兼容现有 WebSocket 库（ws 包原生支持），不改变 URL 结构。

#### 方案 B：握手后认证（两阶段）

1. 客户端先建立不带 Token 的 WebSocket 连接
2. 连接建立后，客户端发送 `{ type: "auth", token: "<proxyToken>" }` 消息
3. 后端验证 Token，成功后返回 `{ type: "auth_ok" }`，失败则关闭连接（code=4001）

**优点**：Token 完全不暴露在网络层。
**缺点**：需要增加认证状态机，连接建立后未认证前不能处理其他消息。

### 兼容性要求

- **向后兼容**：后端需同时支持旧的 URL 查询参数方式（至少 2 个版本周期），便于客户端平滑过渡
- **过渡期**：如果 URL 参数和 Header 同时存在，以 Header 为准
- 客户端将在后端支持 Header 方式后切换，之后逐步废弃 URL 参数

### 验收标准

1. WebSocket 端点支持通过 `Sec-WebSocket-Protocol` 头（方案 A）或握手后消息（方案 B）传递 Token
2. 不传 Token（既无 Header 也无 URL 参数）时返回 401 关闭连接
3. 旧的 URL 参数方式仍可工作（过渡期）
4. Nginx access log 中不出现 Token 明文

## M-6: 更新包签名验证（P2）

### 问题描述

当前更新流程：
1. 客户端请求 `https://u.zdzz.top/api/node-selector.json` 获取更新信息
2. 响应中包含 `downloadUrl` 和 `sha256` 字段
3. 客户端下载安装包并校验 SHA-256

问题：下载 URL 和 SHA-256 来自同一个 API 响应。若更新 API 被攻破（DNS 劫持、服务器入侵），攻击者可以同时替换安装包和哈希值，使哈希校验形同虚设。

### 需求

更新 API 响应增加签名信息，客户端可验证签名来源可信。

#### 方案：GitHub Release 签名 + API 签名双重校验

更新 API 响应新增字段：

```json
{
  "version": "1.5.0",
  "releaseNotes": "...",
  "downloadUrl": "https://github.com/.../releases/download/v1.5.0/...",
  "sha256": "abc123...",
  "signature": "-----BEGIN PGP SIGNATURE-----\n...\n-----END PGP SIGNATURE-----",
  "signatureMethod": "pgp",
  "publicKeyId": "zhengddzz"
}
```

**字段说明**：
- `signature`：对 SHA-256 哈希值的 PGP 签名（Base64 或 ASCII Armor 格式）
- `signatureMethod`：签名方法，当前仅支持 `pgp`
- `publicKeyId`：公钥标识，客户端可据此从可信渠道获取公钥

### 客户端处理逻辑

客户端侧已实现 SHA-256 校验，新增签名验证：

1. 下载安装包 → 计算 SHA-256
2. 用预置公钥验证 `signature` 是否为对 SHA-256 值的有效签名
3. 签名验证失败 → 拒绝安装，提示用户"更新包签名验证失败，可能已被篡改"
4. 签名验证通过 → 继续安装

### 公钥分发

客户端将在应用内硬编码发布者公钥指纹（SHA-256），不依赖网络获取。后端只需确保签名使用对应的私钥生成。

### 验收标准

1. 更新 API 响应包含 `signature`、`signatureMethod`、`publicKeyId` 字段
2. `signature` 是对 `sha256` 字段值的 PGP 签名
3. 签名使用固定的发布者私钥生成（每次 Release 保持一致）
4. `signature` 字段为空时，客户端将回退到仅 SHA-256 校验（不阻断更新，但日志告警）

## I-1: OAuth Client ID 动态获取（Info）

### 问题描述

qzhua OAuth Client ID 硬编码在前端开源代码中：

```typescript
export const QZHUA_OAUTH_CLIENT_ID = "019d5ce39a9b728fa1b5565be72d84ca";
```

虽然 `client_secret` 为空（公开客户端模式），风险较低，但暴露可能被用于：
- 撞库测试 / 暴力枚举
- 构造钓鱼授权链接
- 在第三方应用中冒用 Client ID

### 需求

后端提供接口返回 OAuth 配置信息，客户端启动时动态获取：

```
GET /api/oauth/config

响应:
{
  "success": true,
  "data": {
    "issuer": "https://account-api.qzhua.net",
    "clientId": "019d5ce39a9b728fa1b5565be72d84ca",
    "scope": "openid profile email phone offline_access chmlfrp_api"
  }
}
```

### 客户端处理逻辑

1. 应用启动时请求 `/api/oauth/config` 获取配置
2. 缓存到内存（不持久化），每次启动刷新
3. 请求失败时使用内置的 fallback 值（保证离线可用）
4. 移除前端代码中的硬编码 Client ID，改为从后端动态获取

### 验收标准

1. `GET /api/oauth/config` 返回 `issuer`、`clientId`、`scope` 三个字段
2. 接口无需鉴权（公开接口，OAuth Client ID 本身不算敏感）
3. 响应设置 `Cache-Control: max-age=3600`（1 小时缓存）
4. 客户端请求失败时使用 fallback 值，不影响正常使用
